# 第一版设计：减交互与切换成本

状态：2026-10-11 用户已批准本设计与本仓库 + Pi 试点范围。

## Scope

修改本地流程提示与直接入口，沿用现有脚本、状态和材料模型。默认路径改为主线程连续工作，不建设新模式或自动判定器。

| 拟改文件 | 责任 |
| --- | --- |
| `.trellis/workflow.md` | 调整分流、状态提示、Pi 执行路径、问题与授权规则、检查及知识判断去重；保留阶段编号和标记 |
| `.pi/prompts/trellis-start.md`、`.pi/prompts/trellis-continue.md` | 与本地 workflow 对齐；不再强制小请求建任务或已批准事项重审 |
| `.agents/skills/trellis-start/SKILL.md`、`.agents/skills/trellis-continue/SKILL.md` | 本会话实际加载的共享入口；以 workflow 为准，不保留相反的硬编码路由 |
| `.pi/skills/trellis-brainstorm/SKILL.md` | 合并独立澄清问题，按结论更新材料；保留任务规划的一次实施批准 |
| `.pi/skills/trellis-before-dev/SKILL.md` | 无任务直接处理时只加载相关规范；有任务时按现有材料读取 |
| `.pi/skills/trellis-check/SKILL.md` | 主线程可直接使用、复用同一输入状态的证据，统一一次 spec 判断 |

现有 trellis-update-spec 继续作为按需调用的工具；不改其有效工程契约要求。finish-work、代理角色定义、脚本、公共模板和全局规则均不改。本地定制不等于发布产品默认行为；更新时保留定制，不改模板 hash 来伪装同步。

## Contracts

### 分流与当前任务

- 无任务：纯问答/只读调查直接响应；明确低风险局部修改直接处理；需要持续跟踪或复杂/高风险工作按现有同意机制创建任务并规划。
- 有任务且请求属于当前范围：沿用其规划或执行状态。属于 planning 的修改不借“小修改”名义绕开实施批准。
- 有任务但请求无关：问答可直接回应，不切换指针；明确独立的新开发工作先按范围分流，不能默认为当前任务续作。
- 小修改中发现权限、持久化、跨包契约或未决架构问题时停止扩大范围，转入任务规划；不在事后补文档假装事前已批准。

### 授权与提问

- 已有材料能回答的事实先读取；不要求用户重复提供。
- 相互独立的待决问题可一次列出，有依赖的问题顺序讨论；不规定每条用户消息后必须重写全部 PRD。
- 同一方案已批准且无实质变更时，继续或重启会话不重新审批。仅文件存在不能证明曾获批准；证据不可恢复时才询问。
- “继续规划”“保存交接”“计划我看看”不构成实施授权；本任务是在后续明确确认试点计划后获得实施批准。
- 用户对代码修改的同意不覆盖额外运行验证、依赖安装、Git 或外部操作；本版不修改既有权限规则。

### 执行与上下文

- Pi 默认在主线程读必要规范、实施、调用 check skill；保留按需委派能力及 Active task 派发协议，不要求新开实现/检查代理。
- 现有 JSONL 准备与 start 就绪要求暂时保留。第一版减少代理切换，尚不承诺减少上下文清单文件；避免通过改提示词意外绕开当前校验。
- 使用已有 planning/in_progress 状态和当前 Pi 对应的普通状态块；不新增 pi.dispatch_mode 或 Pi 专用伪状态。

### 验证证据与知识判断

- 检查结果必须能说明命令/检查项、覆盖范围、对应输入状态和环境、结果或未执行原因；记录在现有实现记录或可恢复会话中，不创建新的结果数据库或缓存系统。
- 相同状态且证据完整时复用；输入或环境改变只重做受影响部分，范围不足则补足。最终范围不缩小为最后一小段 diff。
- 没有授权执行的项目检查明确标为未执行，不能把本地文档审阅称作运行或 CI 通过。
- spec 是否需更新由完整交付检查统一判断一次，3.3 负责必要的实际更新，3.4 复用结论；只有新增契约/发现或结论缺失时补判。

## Data Flow

用户请求 → 判断是否属于当前任务及是否需要记录 → 直接处理或现有任务规划 → 主线程实施/必要委派 → 收集或复用有效检查证据 → 一次知识沉淀判断 → 交付 → 用户另行授权的现有 Git 收尾。

workflow 是本地行为规则来源；start/continue 和 skills 引用并执行同一规则。运行时仍只读取原有状态及标记，不修改任务状态写入者。

## Tradeoffs

- 先本地 Pi 试点，改动面较小，但不会让其他用户安装的 Trellis 自动变轻；全产品推广单独规划。
- 暂留三文档与 JSONL，所以第一版主要降低交互和代理切换成本，不宣称完成全部轻量化。
- 判断由 agent 按明示边界进行，不增加机械的文件数阈值。高风险边界不明确时需要澄清。
- 不修改全局权限规则；它们引起的额外运行授权仍存在，不能通过本地提示词绕过。

## Rollout and Rollback

批准后只修改表中八个本地文件，保留旧任务与用户其他变更。保持 workflow 标记配对、阶段编号及现有 JSONL/任务结构约定；不运行 trellis update 或重新生成平台目录。

按 workflow → 入口/skills 顺序实施，作为一个一致变更集合交付。回退时只撤销本任务对这八个文件的变更，不重置工作区、不回滚其他提交、不删除任务记录。若必须改脚本、公共模板、测试或全局规则才能实现，先报告证据和范围变化，不自行扩展。
